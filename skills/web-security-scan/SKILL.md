# Web Security Scan (เช็คลิสต์ 189 รายการ)

Skill นี้ทำให้การตรวจความปลอดภัยเว็บเป็นกระบวนการซ้ำได้: เก็บข้อมูล → แปลผล → ออกรายงาน Excel ที่มอบหมายงานต่อได้ทันที

## กติกาสำคัญ — อ่านก่อนเริ่มเสมอ

**ตรวจได้เฉพาะเว็บที่ผู้ใช้เป็นเจ้าของหรือได้รับอนุญาตเป็นลายลักษณ์อักษร** ถามยืนยันก่อนเริ่มทุกครั้งถ้ายังไม่ชัด การสแกนเว็บคนอื่นโดยไม่ได้รับอนุญาตผิดกฎหมายในไทย (พ.ร.บ. คอมพิวเตอร์ฯ) — ถ้าโดเมนดูเหมือนของบุคคลที่สาม (เช่น เว็บคู่แข่ง, marketplace, ธนาคาร) ให้ปฏิเสธและอธิบายเหตุผล

**Skill นี้ทำเฉพาะการตรวจแบบไม่รุกราน (passive / read-only)** — ดู header, TLS handshake, ขอ URL ปกติ, ดู DNS, ตรวจ dependency ในเครื่อง สิ่งที่ **ไม่ทำ**: ยิง payload เจาะระบบ, brute force, DoS, sqlmap, การทดสอบที่แก้ไขข้อมูลจริง หากผู้ใช้ต้องการทดสอบเชิงรุก ให้ออกแบบ **ขั้นตอนทดสอบด้วยมือ** ให้เขาไปทำบน staging แทน ไม่เขียนสคริปต์โจมตีให้

## เลือกโหมดก่อน

ถามผู้ใช้ (หรืออนุมานจากบริบท) ว่าอยู่ในสถานการณ์ไหน:

| โหมด | ใช้เมื่อ | ครอบคลุม |
|---|---|---|
| **A. Quick check** | อยากรู้คร่าว ๆ เร็ว ๆ / ยังไม่อยากรันสคริปต์ | ~20 ข้อ ทำได้จาก `WebFetch` เท่านั้น |
| **B. Full scan** | ต้องการผลจริงจัง มีสิทธิ์เข้า server หรือรัน terminal ได้ | ~90 ข้อ ผ่านสคริปต์ `scan.sh` |
| **C. Manual review** | ตรวจ logic, สิทธิ์, PDPA ที่สคริปต์ทำแทนไม่ได้ | ~99 ข้อที่เหลือ |

โดยทั่วไปแนะนำ B → แล้วตามด้วย C สำหรับข้อที่เหลือ

---

## โหมด A — Quick check (ทำเองได้ทันที)

ใช้ `WebFetch` ดึงหน้าเว็บของผู้ใช้ แล้วอ่านหาสิ่งเหล่านี้จาก HTML/JS ที่ได้มา:

- `<script src=...>` จากโดเมนภายนอก — มี `integrity=` (SRI) ไหม, โดเมนน่าเชื่อถือไหม
- ทรัพยากรที่ยังเป็น `http://` (mixed content)
- key/token/secret ที่ฝังใน inline JS — ค้นคำว่า `apiKey`, `api_key`, `secret`, `token`, `Bearer`, `AIza`, `sk_live`
- HTML comment ที่เปิดเผย path ภายในหรือข้อมูลระบบ
- meta generator / เส้นทางไฟล์ที่บอกว่าใช้ CMS หรือ framework อะไร เวอร์ชันไหน
- tracking pixel (Meta/TikTok/GA) โหลดทันทีก่อนกด consent หรือเปล่า

จากนั้นลองดึง path เหล่านี้เพื่อดูว่าเข้าถึงได้ไหม (เป็นการขอหน้าเว็บปกติ ไม่ใช่การเจาะ):
`/robots.txt` · `/.well-known/security.txt` · `/.env` · `/.git/config` · `/phpinfo.php` · `/package.json` · `/composer.json` · `/backup/` · `/.DS_Store`

**ข้อจำกัดที่ต้องบอกผู้ใช้ตรง ๆ:** `WebFetch` ไม่คืน HTTP response header ดิบ จึงเช็ค HSTS, CSP, X-Frame-Options, cookie flag, TLS version **ไม่ได้** ในโหมดนี้ อย่าเดาว่ามีหรือไม่มี — ให้บอกว่าต้องใช้โหมด B

ใน Claude Code โหมด B รันได้เองใน terminal อยู่แล้ว ถ้าผู้ใช้ยืนยันสิทธิ์ในโดเมนแล้ว ให้ข้ามไปโหมด B เลยแทนที่จะเดาจากโหมด A

---

## โหมด B — Full scan (ผู้ใช้รันสคริปต์)

ทำตามลำดับนี้:

**1. ขอคำยืนยันสิทธิ์ก่อน แล้วรันเอง**

ถามในแชทตรง ๆ ว่าโดเมนนี้เป็นของผู้ใช้หรือได้รับอนุญาตเป็นลายลักษณ์อักษรไหม **ห้ามรันก่อนได้คำตอบ** เมื่อได้แล้วจึงรันผ่าน Bash:

```bash
bash scripts/scan.sh example.com --yes                      # ตรวจจากภายนอกอย่างเดียว
bash scripts/scan.sh example.com --yes --project /var/www/site   # ตรวจ dependency + permission ในเครื่องด้วย
```

`--yes` คือการยืนยันสิทธิ์ที่ผู้ใช้เพิ่งให้ในแชท ถ้ายังไม่ได้ให้ ห้ามใส่ — ปล่อยให้สคริปต์ถามเองใน terminal

ต้องมี `curl` และ `openssl` ส่วน `dig`, `npm`, `composer` มีก็ดี ไม่มีก็ข้าม
สคริปต์เขียนไฟล์ `scan-<domain>-<วันที่>.json` ไว้ใน working directory — อ่านต่อได้เลย ไม่ต้องให้ผู้ใช้อัปโหลดกลับ

**2. แปลผล**

อ่าน JSON แล้ว map เข้ากับหมายเลขข้อในเช็คลิสต์ ดูวิธี map ที่ `references/mapping.md`
อย่าตัดสินเกินหลักฐาน — ถ้าสคริปต์เก็บค่าไม่ได้ (`null` หรือ `skipped`) ให้ผลเป็น "ยังไม่ตรวจ" ไม่ใช่ "ผ่าน"

**3. ออกรายงาน**

```bash
python3 scripts/build_report.py scan-<domain>-<วันที่>.json --out Security_Report_<domain>.html
```

ฟอร์แมตดูจากนามสกุลไฟล์:

| นามสกุล | ได้อะไร | ใช้เมื่อ |
|---|---|---|
| `.html` (**ค่าตั้งต้น — ให้ใช้อันนี้**) | หน้าเดียวจบ เปิดในเบราว์เซอร์ กรอง/ค้นหาได้ พิมพ์เป็น PDF ได้ | **อ่านผล** — สเปรดชีต 189 แถวไม่ใช่ของที่คนอ่านไหว |
| `.xlsx` | 3 ชีต: Summary, Findings, Checklist มีช่อง "ผู้รับผิดชอบ" กับ "กำหนดแก้" | **มอบหมายงาน** — เมื่อจะแจกให้ทีมกรอกว่าใครแก้ข้อไหน |

ออกพร้อมกันทั้งสองแบบ: `--also Security_Report_<domain>.xlsx`

HTML ไม่ต้องลงอะไรเพิ่ม · `.xlsx` ต้องมี `openpyxl` (`pip install openpyxl`) ถ้าไม่มีให้บอกผู้ใช้ก่อน อย่าเงียบแล้วข้ามรายงาน

ไฟล์ HTML เป็นไฟล์เดียวจบ ไม่เรียก CDN ไม่มี asset ภายนอก — เปิดออฟไลน์ได้ และ **ห้ามเอาไป host หรืออัปขึ้นบริการภายนอก** มันคือเอกสารที่บอกว่าระบบของเจ้าของเว็บพังตรงไหน ส่งเป็นไฟล์ให้เจ้าตัวเท่านั้น

**4. สรุปในแชท**

ตอบสั้น ๆ ไม่เกิน ~10 บรรทัด: จำนวนข้อที่ไม่ผ่านแยกตามระดับ, 3 อันดับที่ต้องแก้ก่อน พร้อมเหตุผลว่าทำไมเรื่องนั้นอันตรายกับธุรกิจของเขาโดยเฉพาะ แล้วบอก path ของไฟล์รายงาน (เปิดด้วย `open <ไฟล์>.html`) อย่าไล่อ่านทุกข้อในแชท — ไฟล์มีให้แล้ว

บอกจำนวน "ยังไม่ตรวจ" ด้วยเสมอ ไม่ใช่แค่ผ่าน/ไม่ผ่าน — ข้อที่ตรวจไม่ได้คือข้อที่ยังไม่รู้คำตอบ ไม่ใช่ข้อที่ปลอดภัย

## โหมด C — Manual review

ข้อที่สคริปต์ทำแทนไม่ได้ (Business Logic, IDOR, สิทธิ์ข้าม role, PDPA process, backup) ให้ช่วยผู้ใช้ตรวจแบบ **ถามทีละชุด** ไม่ใช่ยิงคำถาม 99 ข้อรวด

ใช้ `AskUserQuestion` ถามครั้งละไม่เกิน 3 ข้อ เรียงตามความเสี่ยง เริ่มจากหมวดที่เกี่ยวกับเงินและข้อมูลลูกค้าก่อนเสมอ (หมวด 12 Business Logic → 6 Access Control → 5 Authentication → 13 PDPA)

สำหรับข้อที่ต้องทดสอบจริง ให้เขียนเป็น **ขั้นตอนทำมือ** ที่ผู้ใช้ทำตามได้ เช่น:

> **ทดสอบ IDOR (ข้อ 77)** — สร้างบัญชีทดสอบ 2 บัญชี A และ B
> 1. ล็อกอินเป็น A เปิดหน้าคำสั่งซื้อ จด URL เช่น `/order/1052`
> 2. ล็อกเอาต์ ล็อกอินเป็น B แล้วเปิด `/order/1052` ตรง ๆ
> 3. ถ้า B เห็นออเดอร์ของ A → **ไม่ผ่าน (Critical)**

## หลักการเขียนรายงาน

- **จัดลำดับตามความเสียหายจริง ไม่ใช่ตามความง่ายในการหา** — `.env` หลุดสำคัญกว่า Permissions-Policy หายเสมอ
- **เชื่อมโยงกับธุรกิจของผู้ใช้** ถ้ารู้ว่าเขาขายของออนไลน์ ให้ชี้ว่าข้อไหนกระทบยอดขาย ข้อมูลลูกค้า หรือ PDPA
- **ทุก finding ต้องมีวิธีแก้ที่ก๊อปไปวางได้** ไม่ใช่แค่บอกว่า "ควรตั้งค่า CSP"
- **ระบุความมั่นใจ** — แยกให้ชัดระหว่าง "ตรวจแล้วพบว่าไม่ผ่าน" กับ "ตรวจอัตโนมัติไม่ได้ ต้องยืนยันเอง"
- **ห้ามนับ "ตรวจไม่ได้" เป็น "ผ่าน" เด็ดขาด** — สองกรณีที่เกิดจริงและสคริปต์จัดการให้แล้ว: openssl รุ่นใหม่ไม่ยอมต่อ TLS 1.0/1.1 เลยถามเซิร์ฟเวอร์ไม่ได้ (ข้อ 1) และเว็บที่ตอบ 200 ให้ทุก path ทำให้ "ไฟล์หลุด" ตัดสินจาก status ไม่ได้ (ข้อ 30–41) ทั้งสองกรณีรายงานจะขึ้น "ยังไม่ตรวจ" พร้อมบอกวิธีตรวจต่อ — ให้ย้ำกับผู้ใช้ อย่าแปลงเป็นผ่านเอง
- **อย่าปั่นความกลัว** จำนวน finding ไม่ใช่ตัวชี้วัด เว็บที่ไม่ผ่าน 40 ข้อระดับ Low ปลอดภัยกว่าเว็บที่ไม่ผ่าน 2 ข้อระดับ Critical
